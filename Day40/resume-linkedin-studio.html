How this was built

The brief, distilled

A general-purpose resume & LinkedIn assistant. Input is free-pasted resume text plus an optional job description. Output is complete, copy-paste-ready rewritten copy — not a score, not a critique, a finished draft. Tone: professional, corporate-HR register.

System prompt design

  • Role framing — the model is cast as a senior resume writer and LinkedIn strategist, which anchors vocabulary, structure, and confidence level in the output rather than a generic "helpful assistant" voice.
  • Anti-fabrication constraint — the single highest-risk failure mode for this domain is a model inventing metrics, job titles, or dates to make bullets sound stronger. The prompt explicitly forbids this and instructs the model to insert visible placeholders like [add %/number] instead.
  • ATS-safe formatting rules — no tables, no decorative unicode, standard section headers — because the output is meant to be pasted directly into a resume that may pass through applicant tracking systems.
  • Fixed output schema — the prompt mandates specific markdown headers (## Professional Summary, ## Rewritten Experience, etc.) purely so this interface can reliably split the response into the Resume and LinkedIn tabs without fragile parsing.
  • Edge-case handling — explicit instructions for sparse resumes (students/freelancers), non-English input, missing job descriptions, and non-resume input, so the assistant degrades gracefully instead of guessing.

UI & design decisions

  • Letterhead / memo motif — the whole interface is framed as a memo being drafted and stamped, which mirrors the domain (a recruiter reviewing and approving a document) more than a generic chat window would.
  • Faint ruled-paper background and a red "approved" stamp on the finished draft reinforce the idea of a physical document moving from intake to sign-off, rather than a chatbot reply.
  • Two-pane layout — intake on the left, draft on the right — so the source material and the rewritten result are visible side by side rather than buried in a scrolling conversation.
  • Typography — Source Serif 4 for headings (editorial, letterhead feel), Inter for body copy (readable at length), IBM Plex Mono for labels and metadata (gives it a "form/document" utility feel).

Ideas for extending this

  • Tools: connect a PDF/DOCX parser so users can upload a resume file directly instead of pasting text; add a real ATS keyword-match tool that diffs the job description against the resume programmatically.
  • Memory: remember a user's target roles and past drafts across sessions, so follow-up requests ("make it punchier," "shorten for a 1-page limit") don't require re-pasting everything.
  • Multi-step workflow: split into a pipeline — extract structured data from the resume, ask a clarifying question about missing metrics, then generate the final draft — rather than one single-shot generation.
  • Export: generate a downloadable, properly formatted .docx or .pdf directly from the returned markdown.
