PART 1

System Architecture

ContentSpark — System Architecture

Status: Approved Day 2 design, matches PRD v1.0 and Implementation Blueprint Repo location: Day51/ (monorepo: 60-days-challenge-on-Claude)

1. Overview

ContentSpark is a single-user, client-side-heavy web application with exactly one server-side responsibility: securely calling the Claude API. There is no traditional backend server, no database server, and no authentication layer — all of which are deliberate scope decisions from the PRD to fit a 1–2 hour/day, 9-remaining-day budget.

Save result to history" --> LS

3. Data Flow

  1. App load: Vercel serves the static React build. React reads contentspark_clients and contentspark_history from localStorage to populate the Dashboard.
  2. Client management: All create/edit/delete operations for client profiles happen entirely in the browser — React state updates localStorage directly via utils/storage.js. No network request involved.
  3. Content generation: When “Generate Content” is clicked, the client’s profile data is sent to /api/generate (Vercel serverless function). This is the only network call that leaves the browser besides the initial page load.
  4. AI call: The serverless function reads ANTHROPIC_API_KEY from Vercel’s environment variables (never sent to the browser), builds a structured prompt, and calls the Claude API.
  5. Response handling: The parsed JSON result flows back to the browser, renders in GenerationResult, and is saved to contentspark_history in localStorage.

4. Request Lifecycle (Generate Content Flow)

sequenceDiagram participant U as Sadia (User) participant R as React App participant V as Vercel Function<br/>/api/generate participant C as Claude API U->>R: Click "Generate Content" R->>R: Set isLoading = true, show LoadingSkeleton R->>V: POST /api/generate { niche, tone, goal, pastPostExamples } V->>V: Read ANTHROPIC_API_KEY from env V->>V: Build system + user prompt V->>C: messages.create(...) alt Success C->>V: JSON text response V->>V: Parse & validate JSON shape V->>R: 200 { ideas, captions, hashtags, visualDirection } R->>R: Render GenerationResult R->>R: Save entry to contentspark_history (localStorage) else Failure (network / parse / API error) C-->>V: Error / malformed response V->>R: 4xx/5xx { error: "message" } R->>R: Show friendly error state end R->>U: Display result or error

5. AI Interaction Details

  • Model: claude-sonnet-4-6
  • Call pattern: One request per “Generate” click. No streaming, no conversation history (each generation is stateless and independent).
  • Prompt structure:
    • System prompt: instructs Claude to act as a social media content strategist and to return strict JSON only (no markdown, no commentary) with keys ideas, captions, hashtags, visualDirection.
    • User message: dynamically built from the selected client’s niche, tone, goal, and pastPostExamples.
  • Output contract: { ideas: string[], captions: string[], hashtags: string[], visualDirection: string } — validated with a try/catch around JSON.parse in the serverless function before returning to the client.

6. External Services

Service Purpose Tier
Anthropic API Content generation Pay-as-you-go (API key from console.anthropic.com)
Vercel Hosting (static app + serverless function) Free (Hobby)
GitHub Version control, triggers Vercel auto-deploy Free

No other external services (no database provider, no auth provider, no analytics, no image hosting) are used in v1.0 — consistent with the PRD’s “free-tier only, minimal moving parts” non-functional requirement.

7. Security Notes

  • ANTHROPIC_API_KEY lives only in .env.local (local dev, gitignored) and Vercel’s Environment Variables (production). It is read exclusively inside api/generate.js, which runs server-side — it is never bundled into the React app or sent to the browser.
  • Because there’s no authentication and no server-side database, there is no user data at risk beyond what already lives in the user’s own browser (localStorage), which is standard for a single-user local tool.
PART 2

Data Schema

ContentSpark — Data Schema (localStorage)

Status: Approved Day 2 design Storage engine: Browser localStorage (no external database — see ARCHITECTURE.md for rationale)

1. Overview

There is no traditional database in v1.0. Two JSON arrays are stored under fixed localStorage keys, and all reads/writes are centralized in src/utils/storage.js so no component ever touches localStorage directly. This keeps the “schema” simple but still deserves the same rigor as a real database design — field types, constraints, and relationships are all defined below.

2. Collections

2.1 contentspark_clients → ClientProfile[]

Field Type Required Constraints
id string (UUID) Yes Generated via crypto.randomUUID(); primary key
name string Yes Non-empty; max ~80 chars (UI-enforced)
niche string Yes Non-empty; e.g. “bakery”, “fitness coach”
tone string Yes Non-empty; e.g. “fun”, “elegant”, “bold”
goal string Yes Non-empty; e.g. “promote a sale”, “boost engagement”
pastPostExamples string No Free text, can be empty string; no max length enforced (large text handled via overflow-y-auto per Blueprint Day 9)
createdAt string (ISO 8601) Yes Set once at creation, never modified

2.2 contentspark_history → GenerationHistoryEntry[]

Field Type Required Constraints
id string (UUID) Yes Generated via crypto.randomUUID(); primary key
clientId string (UUID) Yes Foreign key → ClientProfile.id (soft reference, app-enforced, no DB-level constraint)
ideas string[] Yes 3–5 items (enforced by AI prompt, not schema)
captions string[] Yes Same length as ideas, index-matched
hashtags string[] Yes Variable length
visualDirection string Yes Non-empty
createdAt string (ISO 8601) Yes Set once at creation

3. Relationships

erDiagram ClientProfile ||--o{ GenerationHistoryEntry : "has many" ClientProfile { string id PK string name string niche string tone string goal string pastPostExamples string createdAt } GenerationHistoryEntry { string id PK string clientId FK string_array ideas string_array captions string_array hashtags string visualDirection string createdAt }

One ClientProfile has many GenerationHistoryEntry records. The relationship is one-to-many, enforced entirely in application code (getHistory(clientId) filters by clientId) since localStorage has no referential integrity.

4. Constraints & Rules

  • Orphaned history: If a client is deleted, their history entries become orphaned (unreachable, since no UI lists history without a client). Per Blueprint Day 9, the decision is: leave orphaned entries harmless rather than cascade-delete, to keep deleteClient() simple. This is documented here so it’s an intentional decision, not a bug.
  • No duplicate IDs: crypto.randomUUID() guarantees uniqueness; no manual ID collision handling needed.
  • No cross-field validation needed: Each field is independent; the only relationship is clientId referencing an existing ClientProfile.id, checked implicitly (a history entry is only ever created immediately after a successful generation for a currently-loaded, valid client).

5. Schema Validation Against PRD Functional Requirements

PRD Requirement Supported By
FR-1: Create client profile with name, niche, tone, goal, past posts ClientProfile — all fields present
FR-2: View list of all client profiles getClients() reads full contentspark_clients array
FR-3: Edit existing client profile saveClient() updates by matching id
FR-4: Delete client profile deleteClient(id) filters array by id
FR-6: Send niche/tone/goal/pastPosts to Claude All 4 fields exist on ClientProfile
FR-7: Display ideas, captions, hashtags, visual direction All 4 fields exist on GenerationHistoryEntry
FR-11: Auto-save every generation to history saveHistoryEntry() called right after successful generation
FR-12: View chronological history per client getHistory(clientId) + sort by createdAt descending
FR-13: Reopen a past generation Full entry retrieved by id, all fields present to re-render GenerationResult
FR-14: Delete a history entry deleteHistoryEntry(id) filters array by id

Every functional requirement from the PRD maps cleanly onto this schema — no gaps found.

PART 3

API Design

ContentSpark — API Design

Status: Approved Day 2 design Note: Because there is no backend database (see ARCHITECTURE.md), ContentSpark has exactly one real HTTP API endpoint. All client profile and history operations (create/edit/delete/list) are client-side functions against localStorage — not network calls — and are documented separately for completeness.

1. HTTP Endpoint

POST /api/generate

Purpose: Securely call the Claude API on behalf of the browser, using a server-side API key, and return structured content for a given client profile.

Request

POST /api/generate
Content-Type: application/json
{
  "niche": "string, required",
  "tone": "string, required",
  "goal": "string, required",
  "pastPostExamples": "string, optional (can be empty string)"
}

Response — Success (200)

{
  "ideas": ["string", "string", "string"],
  "captions": ["string", "string", "string"],
  "hashtags": ["string", "string", "..."],
  "visualDirection": "string"
}
  • ideas and captions are index-matched (idea[0] pairs with caption[0]).
  • 3–5 items expected in ideas/captions, enforced via prompt instruction, not strict schema validation.

Validation

Rule Behavior if violated
niche, tone, goal must be non-empty strings Return 400 before calling Claude
pastPostExamples may be missing or empty No error — prompt handles gracefully
Response from Claude must be valid JSON matching the expected shape If JSON.parse fails, return 502 with a generic error message (never leak raw Claude output or stack traces to the client)

Authentication

None. This is a single-user app with no login system (per PRD). The endpoint is technically public if someone finds the URL, but it does nothing without valid client-shaped input, and the API key itself is never exposed. (Acceptable risk for a v1.0 personal tool — noted here explicitly as a conscious tradeoff, not an oversight.)

Error Cases

Scenario HTTP Status Response Body
Missing/empty required field (niche, tone, or goal) 400 { "error": "Missing required client information." }
ANTHROPIC_API_KEY not configured (misconfigured deploy) 500 { "error": "Server configuration error." }
Claude API call fails (network, rate limit, timeout) 502 { "error": "Something went wrong generating content. Please try again." }
Claude returns non-JSON or malformed JSON 502 { "error": "Something went wrong generating content. Please try again." }
Method other than POST 405 { "error": "Method not allowed." }

2. Client-Side Data Operations (Not HTTP — for completeness)

These live in src/utils/storage.js and operate directly on localStorage. Documented here so the “full CRUD surface” of the app is visible in one place, even though none of it is a network API.

Function Purpose Equivalent to
getClients() Read all client profiles GET /clients
getClientById(id) Read one client profile GET /clients/:id
saveClient(client) Create (no id) or update (has id) a client POST /clients or PUT /clients/:id
deleteClient(id) Delete a client profile DELETE /clients/:id
getHistory(clientId) Read all history entries for a client GET /clients/:id/history
saveHistoryEntry(entry) Create a history entry POST /history
deleteHistoryEntry(id) Delete a history entry DELETE /history/:id

If a future version (v2) migrates to a real database, this table is effectively the REST API spec to implement — the function names and responsibilities can map almost directly onto real endpoints.

2. What Each Folder Is Responsible For

Folder / File Responsibility
docs/ All design documentation (today’s deliverables). Not shipped in the built app — reference material only.
api/ Server-side code. Currently just one file (generate.js). This is the only folder where the Claude API key may ever be referenced.
src/pages/ Route-level components — one per screen (Dashboard, ClientForm, ClientDetail). Each owns its own page-level state and data loading.
src/components/ Reusable, presentational pieces used across pages (cards, buttons, result display). No component here should talk to localStorage directly.
src/utils/ All logic that isn’t a UI component: storage.js (data layer) and api.js (network layer). Pages call these; components never do.
.env.local Local secret storage. Never committed (already in .gitignore per Day 2 setup).

3. Why This Structure

  • Pages vs. components separation keeps route-level concerns (data loading, navigation) out of reusable UI pieces — matches the Blueprint’s Day 3–7 build order exactly, so no restructuring will be needed mid-build.
  • utils/ as the only data/network layer means localStorage keys and API call logic exist in exactly one place each — easy to update later (e.g. if v2 swaps localStorage for a real database, only storage.js changes, not every component).
  • api/ isolated from src/ is a Vercel convention (file-based routing for serverless functions) and doubles as a hard boundary: nothing in src/ should ever import from api/, which is how the API key stays server-side.
  • docs/ inside Day51/ keeps all project artifacts (design + code) together in one place within the monorepo, so anyone opening Day51/ sees the complete picture.
