01 / Foundations — The Event Loop

Before touching a single Promise, you need a mental model of how JavaScript actually executes code. Everything about async behavior — why setTimeout(fn, 0) doesn't run immediately, why promises "jump the queue" ahead of timers — falls out of one simple machine: the event loop.

The single thread, and its helpers

JavaScript itself runs on one thread with one call stack. It can only do one thing at a time. But the environment around it — the browser or Node.js — provides Web APIs (timers, network, DOM events) that run outside that thread. When those finish, they don't jump straight back into your code; they place a callback into a queue, and the event loop only pulls from that queue when the call stack is completely empty.

🍳 Analogy — The kitchen ticket rail

Picture a small kitchen with one chef (the call stack) who can only cook one ticket at a time. When an order needs the grill to slow-cook for 20 minutes, the chef doesn't stand there watching it — they hand it to the grill station (a Web API), clip a reminder to the ticket rail (the queue), and immediately start the next order. Only when the chef is completely free do they glance at the rail and pick up the next ready ticket. The chef never multitasks; the kitchen does.

Two queues, not one

There are actually two waiting lines feeding the event loop, and this distinction is one of the most commonly misunderstood parts of JavaScript:

  • Microtask queue — holds Promise callbacks (.then, .catch, .finally) and queueMicrotask(). This queue is always fully drained before the event loop touches the next item below.
  • Macrotask queue (a.k.a. the "task queue") — holds setTimeout, setInterval, DOM events, I/O callbacks. Only one macrotask runs per event loop tick, then the loop checks microtasks again.

Comparison — callback style vs the queues it creates

Callback-based code 
getUser(id, (user) => {
  getPosts(user, (posts) => {
    getComments(posts, (c) => {

    });
  });
});
Why it gets painful

Each callback nests one level deeper. Error handling has to be repeated at every level, the code drifts right ("pyramid of doom"), and there's no single place to catch a failure from any step. Promises exist specifically to flatten this pyramid — that's Module 2.

✏️ Exercise — Predict the output

Given the code below, write down the order in which the four console.log lines will print, then reveal the answer.

console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
Promise.resolve().then(() => console.log('D'));
console.log('E');

Order: A, E, C, D, B. All synchronous lines (A, E) run first. Then both microtasks (C, D) drain completely, in the order they were queued. Only then does the single macrotask (B) get its turn.

Common misconceptions

  • "setTimeout(fn, 0) runs immediately." It's still a macrotask — it waits for the stack to empty and for all microtasks to drain first.
  • "JavaScript is multi-threaded." The language itself is single-threaded; concurrency comes from the surrounding environment (Web APIs / libuv in Node), not from JS running two lines at once.
  • "Promises run on a separate thread." They don't — their callbacks still execute on the same single JS thread, just scheduled via the microtask queue.

Key takeaways

One thread, one call stack Web APIs run concurrency outside JS Microtasks always drain before the next macrotask Promises = microtasks, setTimeout = macrotask

02 / Promises — States, Chaining & Combinators

A Promise is an object representing a value that isn't ready yet, but will be — eventually, one way or another. It's the primitive that made async code composable instead of nested.

The three states

Every promise starts pending and settles exactly once, into either fulfilled (it has a value) or rejected (it has a reason for failing). Once settled, a promise never changes state again — this immutability is what makes promises reliable to pass around.

Creating and consuming a promise

function orderCoffee(inStock) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (inStock) resolve('☕ Latte ready');
      else reject(new Error('Out of milk'));
    }, 1000);
  });
}

orderCoffee(true)
  .then(msg => console.log(msg))
  .catch(err => console.log('Failed:', err.message))
  .finally(() => console.log('Register closed'));
📦 Analogy — A delivery tracking link

A promise is like the tracking link you get right after placing an online order. The package isn't in your hands yet (pending), but the link is a real object you can act on immediately — you can tell it "when this arrives, text me" (.then) or "if it's lost, email me" (.catch). You never have to keep manually checking; the courier notifies the link when the state changes, exactly once.

Chaining — returning values through .then()

The real power of promises is that .then() itself returns a new promise. Whatever you return inside a .then() callback becomes the fulfilled value of the next link in the chain — including another promise, which gets automatically "flattened."

getUser(id)
  .then(user => getPosts(user.id))   // returns a promise — auto-flattened
  .then(posts => getComments(posts[0]))
  .then(comments => console.log(comments))
  .catch(err => console.log('Any step failed:', err));

One .catch() at the end covers every step above it — a huge readability win over nested callbacks, where each level needed its own error handling.

Combinators — running promises together

Promise.all()

Waits for all to fulfill. Rejects immediately if any one rejects — "all or nothing."

Promise.allSettled()

Waits for all to finish regardless of outcome, and gives you a status report for each — nothing short-circuits.

Promise.race()

Settles as soon as the first promise settles — fulfilled or rejected, whichever happens first wins.

Promise.any()

Settles as soon as the first one fulfills. Only rejects if all of them reject.

✏️ Exercise — Choose the right combinator

You're loading a dashboard that needs three independent widgets. If one widget's API fails, the other two should still render with their own data. Which combinator fits?

Promise.allSettled() — because you want every widget's outcome (success or failure) without one rejection wiping out the results of the other two, which is exactly what Promise.all() would do.

Common misconceptions

  • "The executor function runs asynchronously." It doesn't — the code inside new Promise((resolve, reject) => {...}) runs synchronously, immediately, the moment the promise is constructed.
  • "Forgetting to return inside a .then() is harmless." If you don't return the inner promise, the chain moves on before it settles, and you lose its resolved value entirely.
  • "One .catch() anywhere is enough." A .catch() only catches errors from steps above it in the chain — placed too early, later steps' errors slip through uncaught.

Key takeaways

Pending → Fulfilled / Rejected, once .then() returns a new promise Always return inside .then() all / allSettled / race / any

03 / Async/Await — Syntactic Sugar with Power

async/await doesn't replace promises — it's built directly on top of them. It lets you write asynchronous code that reads like synchronous code, without changing the underlying event-loop mechanics from Module 1.

The two keywords

  • async in front of a function means that function always returns a promise — even if you just return 5, the caller gets a promise that resolves to 5.
  • await can only be used inside an async function. It pauses that function (not the whole program) until the promise settles, then unwraps its value.

Side-by-side: .then() chain vs async/await

Promise chain 
function loadDashboard() {
  return getUser(id)
    .then(user => getPosts(user.id))
    .then(posts => {
      console.log(posts);
      return posts;
    })
    .catch(err => {
      console.log('Error:', err);
    });
}
Async/await 
async function loadDashboard() {
  try {
    const user = await getUser(id);
    const posts = await getPosts(user.id);
    console.log(posts);
    return posts;
  } catch (err) {
    console.log('Error:', err);
  }
}

Same behavior, same microtask timing — just a flatter, top-to-bottom shape that reads like ordinary procedural code.

👩‍🍳 Analogy — Recipe steps vs. sticky notes

A .then() chain is like leaving yourself a trail of sticky notes: "when the water boils, do this; when that's done, do this next." async/await is the same recipe rewritten as ordinary numbered steps: "boil water, wait, add pasta, wait, drain." The waiting still happens — you haven't skipped the timer — you've just stopped writing it as a note-passing relay.

Sequential vs. parallel — the bug almost everyone writes once

Because await pauses the function, writing two independent awaits back-to-back accidentally makes them run sequentially, even when they don't depend on each other:

❌ Accidental waterfall (slow) 
const weather = await getWeather();
const news = await getNews();
// news waits for weather to
// finish first — unnecessary!
// Total time = sum of both.
✅ Run in parallel 
const [weather, news] = await Promise.all([
  getWeather(),
  getNews()
]);
// Both start immediately.
// Total time = the slower
// of the two, not the sum.

Error handling with try/catch/finally

async function checkout(cart) {
  try {
    const payment = await charge(cart.total);
    return payment;
  } catch (err) {
    console.log('Payment failed:', err.message);
    throw err; // re-throw so the caller still knows
  } finally {
    hideSpinner();  // always runs — success or failure
  }
}

✏️ Exercise — Fix the waterfall

Rewrite this function so fetchProfile and fetchSettings run in parallel instead of sequentially:

async function loadAccountPage() {
  const profile  = await fetchProfile();
  const settings = await fetchSettings();
  return { profile, settings };
}
async function loadAccountPage() {
  const [profile, settings] = await Promise.all([
    fetchProfile(),
    fetchSettings()
  ]);
  return { profile, settings };
}

Both requests fire on the same tick; the function only pauses once, for whichever one is slower.

Common misconceptions

  • "await freezes the whole browser/tab." It only pauses the current async function. Other code, UI rendering, and event handlers continue running normally.
  • "An async function's first line always runs asynchronously." Code before the first await runs synchronously, immediately, just like any normal function call.
  • "await works inside .forEach()." forEach ignores returned promises entirely — awaits inside it don't pause the loop. Use a for...of loop or Promise.all with .map() instead.

Key takeaways

async function → always returns a Promise await pauses only that function Independent awaits → use Promise.all try/catch replaces .catch()

04 / Mastery — Real-World Async Patterns

Production code needs more than the happy path. This module covers the patterns you'll actually reach for: retrying flaky requests, cancelling stale ones, and avoiding subtle race conditions.

Retry with exponential backoff

Network calls fail. Instead of giving up immediately, a common pattern retries a few times, waiting progressively longer between attempts so you don't hammer a struggling server.

async function retryWithBackoff(fn, attempts = 3) {
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      if (i === attempts - 1) throw err; // out of tries
      const delay = 2 ** i * 200; // 200ms, 400ms, 800ms...
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

Cancelling stale requests with AbortController

If a user types in a search box and fires three requests, you usually only want the latest one to matter. AbortController lets you cancel promises that would otherwise resolve too late and overwrite fresher data.

let controller;

async function search(query) {
  controller?.abort();          // cancel the previous request
  controller = new AbortController();
  try {
    const res = await fetch(`/search?q=${query}`, {
      signal: controller.signal
    });
    return await res.json();
  } catch (err) {
    if (err.name === 'AbortError') return; // expected, ignore
    throw err;
  }
}
🏁 Analogy — A relay team with a whistle

Firing off requests without cancellation is like sending a new runner down the track every time you blink, without calling back the earlier ones — whichever runner happens to cross the line last "wins," even if they were the first one sent. AbortController is the coach's whistle: the moment a newer runner is sent, the old one is told to stop, so only the most recent result ever gets recorded.

Comparison — Promise.all error behavior vs individual try/catch

❌ One try/catch around Promise.all 
try {
  const [a, b] = await Promise.all([
    taskA(), taskB()
  ]);
} catch (e) {
  // you only know SOMETHING
  // failed — not which one,
  // and the other's result
  // is thrown away entirely.
}
✅ Per-task safety with allSettled 
const results = await Promise.allSettled([
  taskA(), taskB()
]);
results.forEach(r => {
  if (r.status === 'fulfilled')
    console.log(r.value);
  else
    console.log('failed:', r.reason);
});

✏️ Exercise — Spot the race condition

A search box calls search(query) on every keystroke, with no cancellation logic. The user types "ap", then quickly "apple". Why might the results for "ap" flash on screen after the results for "apple"?

Both requests are in flight at once. If the server (or network) happens to respond to "ap" slower than to "apple", the "ap" response arrives second and overwrites the newer, correct "apple" results — even though "apple" was typed later. This is exactly the bug AbortController or a request-id check prevents.

Common misconceptions

  • "Retrying is always safe." Only retry idempotent operations (like GET requests) — blindly retrying a payment POST could charge a user twice.
  • "AbortController cancels the server-side work too." It only stops the client from waiting on / using the response; the server may still finish processing the original request.
  • "More retries is always better." Unlimited retries against a truly down service just adds load; always cap attempts and back off.

Key takeaways

Backoff between retries, cap attempts AbortController cancels stale requests allSettled for independent, isolated failures Only retry idempotent operations

05 / Final Practical Challenge

Put everything together: chaining, parallel execution, error isolation, and retries — in one function.

🏆 Challenge — Build loadDashboard()

You're given three mock async functions (already defined below, simulating a flaky network): fetchUser(), fetchStats() (sometimes fails), and fetchNotifications(). Write an async function loadDashboard() that:

  1. Fetches all three in parallel.
  2. Wraps fetchStats() in retryWithBackoff (provided) since it's the flaky one.
  3. Doesn't let a failure in one call block the other two — use allSettled.
  4. Returns an object { user, stats, notifications }, using null for anything that ultimately failed.
async function loadDashboard() {
  const results = await Promise.allSettled([
    fetchUser(),
    retryWithBackoff(fetchStats, 3),
    fetchNotifications()
  ]);

  const [user, stats, notifications] = results.map(
    r => r.status === 'fulfilled' ? r.value : null
  );

  return { user, stats, notifications };
}

This single function demonstrates every concept from all four modules: parallel execution (Module 3), isolated failure handling via allSettled (Module 2 & 4), and a resilient retry wrapper (Module 4).

📋 Cheat Sheet

// Creating
new Promise((resolve, reject) => { ... })

// Consuming
promise.then(onFulfilled).catch(onRejected).finally(onDone)

// Combinators
Promise.all([p1, p2])        // all-or-nothing
Promise.allSettled([p1, p2]) // every outcome, no throw
Promise.race([p1, p2])       // first to settle
Promise.any([p1, p2])        // first to fulfill

// Async/await
async function f() { await somePromise; }
try { await f(); } catch (e) { }

// Parallel await (not sequential!)
const [a, b] = await Promise.all([taskA(), taskB()]);

// Cancellation
const c = new AbortController();
fetch(url, { signal: c.signal });
c.abort();

Summary notes

The event loop drains the microtask queue (promises) completely before running a single macrotask (timers). Promises give you a chainable, catchable representation of a future value; async/await is the same mechanism wearing synchronous-looking clothes. Master the difference between running things sequentially and in parallel, isolate failures with allSettled, and add retries/cancellation for anything talking to a real network.
